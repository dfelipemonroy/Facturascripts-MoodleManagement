# Plan de Acción — MoodleManagement v2.0

**Documento maestro de implementación**
**Fecha inicio**: 2026-04-16
**Auditoría base**: informe de 166 hallazgos (14 CRÍTICO · 38 ALTO · 46 MEDIO · 39 BAJO · 29 INFO)
**Compromiso del release**: **cero deuda técnica pendiente**. Toda mejora identificada — incluso severidad BAJO e INFO — se implementa antes del tag `v2.0`.
**Estimación total**: ~56 días-persona (≈ 11 semanas a un desarrollador / ≈ 6 semanas a dos).

---

## 1. Principios rectores

1. **Completitud sobre velocidad**. No se skippean hallazgos. Si uno resulta técnicamente inviable, se documenta la razón en este plan y se marca como `SKIP:JUSTIFIED`.
2. **Orden de menor a mayor riesgo**. Se empieza por tareas aisladas, sin acoplamientos, para ganar momentum y reducir regresiones. Los refactors profundos van al final, cuando hay tests y telemetría.
3. **Cada fase termina verde**. Al cerrar una fase: (a) todos sus tests pasan, (b) la app arranca sin warnings nuevos, (c) cron y workers corren limpios 24 h, (d) PR mergeable a `main` sin conflictos.
4. **Migraciones idempotentes**. Todo script SQL debe poder correrse N veces sin efectos adicionales. Uso de `IF NOT EXISTS`, `INSERT IGNORE`, `CREATE OR REPLACE VIEW`.
5. **Back-compat obligatorio**. Mientras dure la fase 8 (refactor `MoodleClient`), la fachada estática sigue exportando todos los métodos actuales como delegates. Los plugins de terceros que dependan del API público no se rompen.
6. **Un hallazgo = un commit mínimo**. Los commits quedan atómicos para facilitar `git bisect` ante regresiones.
7. **Feature flags para cambios de comportamiento**. Introducción gradual controlada por settings del plugin (p.ej. `mm_feature_webhooks_enabled`).

## 2. Convenciones de trabajo

### 2.1 Branching
- Rama base: `v2.0-dev`
- Ramas de fase: `v2.0/fase-NN-slug` (p.ej. `v2.0/fase-02-seguridad-basica`)
- Merge a `v2.0-dev` vía PR con review propio. Tag final `v2.0.0` al completar fase 12.

### 2.2 Commits
Formato Conventional Commits con referencia al hallazgo:
```
<type>(<scope>): <subject> [#AUDIT-<ref>]

Refs: V2.0-ACTION-PLAN §<fase.tarea>
```
Types: `feat`, `fix`, `refactor`, `security`, `perf`, `docs`, `test`, `chore`, `ci`, `style`.

### 2.3 Checklist
Cada tarea se marca en [`V2.0-TASK-CHECKLIST.md`](./V2.0-TASK-CHECKLIST.md) con `- [x]` al cerrar, incluyendo commit hash.

### 2.4 Testing por fase
- Antes de cerrar fase → `phpunit --testsuite MoodleManagement`, `phpstan analyse` y `phpcs` deben salir limpios.
- Smoke manual: lista de pantallas criticas (dashboard, wizard, editCliente, editProducto, listUserMap, detalle UserMap, listEnrolment, certificadoPdf).

### 2.5 Rollback
- Cada fase deja un commit tag `pre-fase-NN`. Si algo revienta en staging, rollback a ese tag.
- Migraciones SQL tienen siempre su DOWN (documentado en cabecera del archivo `Update/vN.sql`).

## 6. Política de rollback

- **Pre-fase tag**: `pre-fase-NN-YYYYMMDD`.
- **Rollback de DB**: cada migración `Update/v2.0.sql` documenta en cabecera su DOWN SQL. Se ejecuta manualmente en emergencia.
- **Rollback de cifrado**: si cifrado falla tras F5.12, helper `Lib/Security/TokenCipher::decryptAll()` restaura tokens a plaintext (modo de emergencia) con autorización manual.
- **Feature flags**: cambios de comportamiento significativos activables vía settings; si un bug aflora, flip flag a false.
